    ObjectIO features¶

    Everything ObjectIO does today, by domain, and how far each part has been proven. A feature on this page exists; one that isn't here doesn't (what is planned is in the roadmap). How each feature works, with its wire format and settings, is in the feature reference and the guides.

    Reading the columns

    • Status: ✅ shipped and covered by end-to-end tests; 🟡 shipped, but not yet proven for production (the gap is named); ✖ not supported, by decision (the reason is given).
    • Guide: where a user or operator reads how to use it.
    • Design: how it works inside.

    How far 0.1.0 has been proven¶

    0.1.0 is the first release, and an early one. S3 and the storage core are tested for production; the data lake APIs, block volumes and file access are previews.

    • S3: ceph s3-tests, 680 of 687 applicable tests pass at the release candidate on Linux x86_64, 679 on Linux arm64; the rest are written down (6 known gaps, and tests caught by another running beside them, which pass alone). None is a bug.
    • The storage core: a 48-hour soak of 84 faults (power cuts, meta leader kills, network partitions, disks pulled and drives lost for good) under 7.02 M acknowledged operations and 1.50 TB written: no acknowledged object lost, no space leaked. The chaos suite on six machines: 81,436 acknowledged writes intact through every fault. Recorded disk writes replayed up to random power-cut points: nothing acknowledged lost.
    • Data lake, block, file: the data lake APIs and block volumes are built and unit- or end-to-end-tested, but not yet tested with real engines (Spark, Trino, pyiceberg) or under a filesystem and a database; file access is not built.

    Adjacent releases upgrade one node at a time, under traffic, with every object readable after (upgrades). The admin API and the CLI may still change between 0.x releases; the release notes say when they do.

    Core¶

    Feature Status Notes Guide Design
    Raw-disk OSD: O_DIRECT, 4 KiB blocks, a write-ahead log ✅ deployment storage engine
    Flush before acknowledge ✅ Each shard fsynced, then its location record; a drive's volatile cache flushed on every write; a failed location record fails the write production storage engine
    One write quorum for every stripe ✅ PUTs, multipart parts, packs and block chunks alike: k + 1 shards (MDS), two copies, or all but g − 1 (LRC), counted on distinct OSDs; 503 short of it (507 when the OSDs are full). Every shard carries its placement group's epoch, and a write placed under an old one is placed again S3 API data protection
    Crash consistency of the OSD ✅ The shard device's and state filesystem's writes recorded and replayed up to random power-cut points: every acknowledged write survives. Run in CI on every merge storage engine
    On-disk format checks ✅ Superblock feature words, protobuf records, strict logs and snapshots disk layout
    Superblock safety ✅ Two copies; a torn one mounts from the other; deletes no longer rewrite it disk layout
    An OSD's disks known by their ids ✅ Each disk's index recorded by the id in its superblock: disks found in any order or at other paths; an OSD missing one, or given one not its own, doesn't start; a blank disk replaces a missing one. Reads and scrub check each block is the shard its location names (object, stripe, length, CRC32C) production storage engine
    OSD metadata store (WAL, on-disk index, bounded cache) ✅ Memory flat with the object count; snapshots streamed, not cloned storage engine
    OSD back in seconds after a restart ✅ An OSD of 10 M shards serves 16.9 s after a power cut; its counts are rebuilt after it serves failure recovery OSD start
    io_uring shard I/O 🟡 The default in Linux release builds; a host that denies io_uring (docker's default seccomp profile) gets pread, with a warning. The data-path end-to-end tests run on it in CI (S3 calls, multipart, repair, restarts, packing, checksums, removed disks); the rest of the suite and the soak on pread Docker I/O levels
    Erasure coding: Reed-Solomon with ISA-L, on x86_64 and arm64 ✅ 4+2 by default. One code on every build, its parity checked against the reference code on both architectures, so amd64 and arm64 nodes mix in one cluster (not yet run as one). A pool takes only profiles with parity that every loss of m shards decodes Linux data protection
    Reads never serve a data shard rebuilt wrong ✅ Each data shard a read rebuilds is checked against its recorded checksum (or a spare parity shard) before it is served; a decode that doesn't check out is tried another way, then fails and reports the stripe for repair data protection
    LRC 🟡 Objects of any length, PUT or multipart, read back with a drive lost; repair built and tested. Survives every loss of its global parity count (LRC 6+2+2: any 2, 88% of 3); not yet through the full end-to-end suite or a soak CLI data protection
    Replica pools (2-way, 3-way) 🟡 Repair built and tested; not yet through the full end-to-end suite or a soak data protection
    End-to-end shard checksums, scrub ✅ Each shard's checksum kept with the object and checked on every read and repair, besides the OSD's own data protection
    Object metadata at quorum ✅ With one or two OSDs down (4+2), PUT, overwrite and DELETE go on; reads get the newest copy, never a deleted object object metadata quorum
    Small-object path ✅ A small object's shards travel with its metadata, one round trip; a small GET reads metadata from a read quorum performance small-object path
    Small-object packing (pack, reconcile, compact) ✅ packing
    Placement: CRUSH2, placement groups, copyset allocator ✅ feature reference topology
    Failure-domain topology (5 levels), locality-aware reads ✅ topologies topology
    Refusing placements the topology can't satisfy 🟡 A validation endpoint; enforcement on write is planned topology
    Storage pools (expand by adding a pool), balancer ✅ A pool's protection scheme is checked when it is made or changed: one the codecs can't keep (no parity, LRC groups of unequal size, no copies) is refused feature reference data protection
    Recovery by placement group ✅ Every pool has PGs whose acting set and epoch are committed before a write uses them; OSDs refuse writes from an older epoch; peering and a state machine per PG failure recovery PG recovery
    Repair after a disk or host is lost ✅ Rebuilt from the surviving shards onto the rest of the cluster, without an operator; parallel across PGs, sized from the drives failure recovery PG recovery
    Degraded objects recorded when written, repaired first ✅ A PUT acknowledged short of shards is recorded in the Raft commit that creates it degraded objects
    An OSD lost for good is re-protected ✅ A drive gone with its metadata, set out: every shard it held is rebuilt elsewhere failure recovery PG recovery
    Backfill ✅ A stripe with two shards on one OSD is re-spread once a distinct OSD can take one PG recovery
    Drain (planned removal of an OSD) ✅ failure recovery
    Full-disk behaviour ✅ Client writes stop at the full ratio (507 StorageFull); the rest is kept for repair; space returns after deletes production
    Meta: Raft (openraft), replicated state, snapshots, log compaction ✅ A node that was down longer than the kept log catches up from a snapshot meta HA meta
    Meta's own Raft log ✅ Sealed segments open from an index; a meta node listens within a second of a power cut, a torn last append cut off meta log
    Bucket listings that cost the same per page anywhere in the bucket ✅ The scan seeks to the continuation marker and past each common prefix: paging through 100,000 keys reads each row once meta
    Meta HA: any node serves, failover, node loss ✅ Leader killed, frozen and replaced under S3 traffic, in multi-process tests and on Kubernetes (3 metas through Helm) meta HA meta
    Meta reads confirmed by a quorum (read index) ✅ The leader answers only while a majority has confirmed it leads within the last second; one cut off from its followers answers UNAVAILABLE within about 3 s, in a multi-process test meta HA meta
    Rolling upgrade, format levels ✅ Meta, then OSDs, then gateways, under traffic; new formats gated until every node runs the new release; tested on every change to main upgrades upgrade path
    RDMA data plane (Mooncake Transfer Engine) 🟡 Single-part erasure-coded objects, behind a flag RDMA data plane

    File¶

    Not built. Files are reached through S3 today; NFS on the same core is on the roadmap.

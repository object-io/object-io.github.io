    Identity and Access¶

    Who can do what in an ObjectIO cluster: tenants and their admins, users and access keys, IAM policies, groups and roles, identity providers, and temporary credentials from an OIDC token (STS).

    Everything here is the admin API under /_admin/*, signed with SigV4 like any S3 request. The management SDKs wrap it for Go and Python.

    Scopes: the system and tenants¶

    Every identity object lives in one scope.

    • The system scope belongs to the operator. Its admin (the credential meta prints on first boot) manages the whole cluster.
    • A tenant is a hard boundary. Its users, groups, roles, policies and buckets are its own. No policy can grant a tenant's identity access to another tenant's bucket: the check happens before any policy is read.

    A tenant admin is a user of the tenant listed in its admin_users. A tenant admin manages everything in the tenant and nothing outside it.

    # As the system admin
POST /_admin/tenants                    {"name": "acme", "display_name": "Acme", "enabled": true}
POST /_admin/users                      {"display_name": "acme-admin", "tenant": "acme"}
POST /_admin/tenants/acme/admins        {"user_id": "<user_id>"}
POST /_admin/users/<user_id>/access-keys {}

    From then on the tenant admin works with its own key. Each call below acts in the caller's own tenant. The system admin can name a tenant with ?tenant= (or "tenant" in a body); a tenant admin can't name another tenant.

    Users and access keys¶
    GET /_admin/users users in scope
    POST /_admin/users {"display_name", "email"?, "tenant"?} create
    GET /_admin/users/{user_id} one user
    PUT /_admin/users/{user_id} {"status"?, "display_name"?, "email"?} update; status is active or suspended
    DELETE /_admin/users/{user_id} delete
    GET /_admin/users/{user_id}/access-keys the user's keys
    POST /_admin/users/{user_id}/access-keys {"scope"?, "operation"?} new key; a scope like s3://bucket/prefix/ confines it
    PUT /_admin/access-keys/{id} {"status": "active" \| "inactive"} turn a key off or back on
    DELETE /_admin/access-keys/{id} delete a key

    Suspend rather than delete when you need to cut someone off now and decide later. A suspended user's keys are all refused, and deactivating a key refuses just that key. Nothing is deleted, and reactivating restores access. Gateways cache credentials for at most 15 seconds, so the change takes effect everywhere within that time.

    A scoped key (one with a scope) can only reach that bucket or prefix, and is refused on the admin API entirely. A credential handed to a workload therefore can't mint itself a wider one.

    Policies¶

    IAM policies are AWS-format JSON documents: Effect, Action, Resource, Condition. They are attached to users, groups or roles. A bucket policy is attached to a bucket instead and set with S3's PUT /{bucket}?policy. The two are evaluated together:

    1. An explicit Deny anywhere wins.
    2. An Allow in an attached policy or the bucket policy grants access.
    3. With no Allow, the bucket's owner is allowed and everyone else is denied.

    No policy means owner-only, not open.
    GET /_admin/policies the tenant's own policies, plus the shared catalogue
    POST /_admin/policies {"name", "policy", "tenant"?, "shared"?} create
    GET /_admin/policies/{name} one policy
    PUT /_admin/policies/{name} {"policy"} replace the document
    DELETE /_admin/policies/{name} delete
    POST /_admin/policies/attach {"policy_name", "user_id" \| "group_id" \| "role_name"} attach
    POST /_admin/policies/detach detach, same body
    GET /_admin/policies/attached?user_id=\|group_id=\|role_name= what's attached

    Policies are per tenant: acme's auditors and globex's auditors are different documents. The system admin can mark a system policy "shared": true so that every tenant can attach it but none can change it.

    The built-in readonly, readwrite and writeonly policies are shared. consoleAdmin (admin:*) is the operator's alone.

    Attaching and detaching take effect immediately on the gateway that made the change, and within 15 seconds on the others.

    Policies support every IAM condition operator, plus IfExists, ForAnyValue:/ForAllValues: and Null. A document using an unknown operator is refused when you save it rather than being silently ignored. Policies written for AWS work unchanged: arn:aws: ARNs and {"AWS": ...} principals mean the same as arn:obio: and {"OBIO": ...}. See condition keys.

    Groups¶
    GET /_admin/groups groups in scope
    POST /_admin/groups {"group_name", "tenant"?} create
    GET /_admin/groups/{group_id} one group, with its members
    DELETE /_admin/groups/{group_id} delete
    POST /_admin/groups/{group_id}/members {"user_id"} add a member of the group's own tenant
    DELETE /_admin/groups/{group_id}/members/{user_id} remove

    A user gets the policies attached to every group it belongs to.

    Roles¶

    A role is a set of policies that someone can take on for a while, rather than an identity of its own. Who may take it on is decided by its trust policy. Today a role is assumed with an OIDC token through STS.
    GET /_admin/roles roles in scope
    POST /_admin/roles {"name", "trust_policy", "description"?, "max_session_seconds"?} create
    GET /_admin/roles/{name} the role and its attached policies
    PUT /_admin/roles/{name} {"trust_policy"?, "description"?, "max_session_seconds"?} update
    DELETE /_admin/roles/{name} delete

    A role's ARN names its scope: arn:obio:iam::acme:role/ci for tenant acme, arn:obio:iam::objectio:role/oncall for the system.

    Identity providers (OIDC)¶

    The operator and each tenant can have their own OpenID Connect provider: Keycloak, Entra ID, Okta, Google, Dex, or any other compliant issuer.

    • The operator's provider signs in system administrators. It is set with the gateway's --oidc-* flags, or stored with "system_admin": true.
    • A tenant's provider signs in that tenant's users. It's stored under the name t-<tenant>, which a tenant admin can create for itself. That also binds it to the tenant.
    PUT /_admin/config/identity/openid/t-acme
{"issuer_url": "https://keycloak.acme.example/realms/acme",
 "client_id": "objectio", "client_secret": "…",
 "claim_name": "groups", "scopes": "openid profile email"}

    claim_name can be a dotted path, such as realm_access.roles for Keycloak realm roles.

    Only the system admin can set system_admin, or edit or delete a provider that has it. Otherwise a tenant admin could point the operator's sign-in at their own IdP.

    Temporary credentials from an OIDC token (STS)¶

    AssumeRoleWithWebIdentity trades an OIDC token for a role's temporary S3 keys. It's the AWS STS call, so AWS SDKs and tools speak it as is. Point them at the gateway's S3 endpoint:

    import boto3

sts = boto3.client("sts", endpoint_url="https://s3.example.com", region_name="us-east-1")
r = sts.assume_role_with_web_identity(
    RoleArn="arn:obio:iam::acme:role/ci",
    RoleSessionName="build-42",
    WebIdentityToken=open("/var/run/secrets/token").read(),
    DurationSeconds=3600,
)
c = r["Credentials"]
s3 = boto3.client("s3", endpoint_url="https://s3.example.com",
                  aws_access_key_id=c["AccessKeyId"],
                  aws_secret_access_key=c["SecretAccessKey"],
                  aws_session_token=c["SessionToken"])

    Which provider can vouch for which role:

    role accepted tokens
    system role (arn:obio:iam::objectio:role/…) the operator's providers only
    tenant role (arn:obio:iam::acme:role/…) that tenant's provider only. For a multi-tenant provider such as Entra organizations, only tokens from the upstream organisation registered to the tenant

    A token from the wrong provider is refused with InvalidIdentityToken, however its claims read.

    The trust policy then decides. Claims are condition keys named after the issuer (without https://): <issuer>:sub, <issuer>:aud, <issuer>:email, <issuer>:groups and any other claim. As in AWS, a trust policy has no Resource.

    {"Version": "2012-10-17", "Statement": [{
  "Effect": "Allow",
  "Principal": {"Federated": "https://keycloak.acme.example/realms/acme"},
  "Action": "sts:AssumeRoleWithWebIdentity",
  "Condition": {
    "StringEquals": {"keycloak.acme.example/realms/acme:aud": "objectio"},
    "ForAnyValue:StringEquals": {"keycloak.acme.example/realms/acme:groups": "ci"}
  }
}]}

    What the credentials can do: what the role's attached policies allow, inside the role's tenant. Detaching a policy affects sessions already issued. A system role is not a system admin.

    How long they last: DurationSeconds is between 900 and the role's max_session_seconds. The default is 3600 and the maximum 12 hours.

    Errors: AccessDenied (trust policy, or no such role: the two are answered the same, so role names can't be probed), InvalidIdentityToken, ExpiredTokenException, ValidationError.

    Session and token signing¶

    Temporary credentials, console sessions and listing continuation tokens are signed with keys derived from a cluster secret. Meta creates the secret once and replicates it through Raft, so every gateway shares it: a session issued by one gateway is honoured by all of them, and nothing about it can be forged from outside. The secret is never exposed by any API.

    ACLs¶

    Buckets are bucket owner enforced, the S3 default since 2023. The bucket owner owns every object, ACLs grant nothing, and access is decided by policies only. ACL reads answer with the owner's FULL_CONTROL. An ACL write that says only that is accepted; any other ACL write is refused with AccessControlListNotSupported. No ACL can make data public: see Public access for how that's done deliberately.

    Docker¶

    ObjectIO ships one multi-stage Dockerfile. Its all target is the image that is published and that the Helm chart runs; per-service targets can be built locally.

    • Fastest demo: the objectio-aio binary (it is not in the image)
    • Kubernetes: see kubernetes.md (make kind-up for a local kind cluster)

    There is no Compose file for running a cluster: the repository's docker-compose.yml holds development tools (build, test, lint), and deploy/monitoring/ a Prometheus and Grafana.

    Image targets¶

    Target Binary Ports Role
    gateway objectio-gateway 9000 S3 / Iceberg / Delta Sharing / /_console/
    meta objectio-meta 9100 (gRPC and Raft), 9101 (metrics), 9102 (admin) Raft metadata
    osd objectio-osd 9200 (gRPC), 9201 (metrics) Object storage daemon
    cli obioctl — Admin CLI
    block-gateway objectio-block-gateway 9300 (gRPC), 10809 (NBD) Block volumes over NBD and gRPC
    all gateway, meta, osd, obioctl, objectio-install, block-gateway, and the console 9000 + internal One image, any service

    Port numbers are the cluster's, used by the Helm chart and every binary's defaults (ports).

    One multi-arch image (linux/amd64, linux/arm64) is published on GHCR, and it carries every service:

    • ghcr.io/object-io/objectio:<tag> (for example v0.1.0-rc.1), also tagged latest — the all target

    It has no entrypoint: name the binary to run, as the Helm chart does. The per-service targets (gateway, meta, osd, cli, block-gateway) are not published; build them locally if you want them. Their default commands pass flags the binaries don't have (--bind, --raft-bind), so always give the arguments yourself:

    docker build --target gateway -t objectio-gateway .

    Both linux/amd64 and linux/arm64 erasure-code with ISA-L and write the same stripes, so a cluster may mix them.

    The published image¶

    The all target packages the service binaries plus the console SPA. You choose the binary at docker run time:

    # The admin CLI against an existing cluster
docker run --rm --network host \
  -e OBJECTIO_ACCESS_KEY -e OBJECTIO_SECRET_KEY \
  ghcr.io/object-io/objectio:v0.1.0-rc.1 \
  obioctl --endpoint http://localhost:9000 user list

# A service: the flags are the binary's own (see configuration.md)
docker run --rm ghcr.io/object-io/objectio:v0.1.0-rc.1 objectio-gateway --help

    The image runs as the non-root user objectio, declares /var/lib/objectio as a volume, and has no curl.

    Running the services in containers¶

    Without Kubernetes, run each service from the image with the flags in Linux: meta with --node-id, --raft-advertise and its data directory on a volume, then the Raft bootstrap calls to its admin port; OSDs with an osd.toml mounted at /etc/objectio/osd.toml; gateways with every meta node's address in --meta-endpoint.

    An OSD on raw block devices needs them passed as devices: and the capability to open them with O_DIRECT:

    services:
  osd1:
    image: ghcr.io/object-io/objectio:v0.1.0-rc.1
    command: ["objectio-osd", "--config", "/etc/objectio/osd.toml"]
    cap_add: [SYS_RAWIO]
    devices: [/dev/nvme1n1:/dev/nvme1n1]
    volumes:
      - ./osd1.toml:/etc/objectio/osd.toml:ro
      - osd1-state:/var/lib/objectio/osd

    Building images locally¶

    # Single-arch, native platform
make docker                 # gateway, meta, osd, cli and all
make docker-gateway         # just the gateway
make docker-all             # the published image's target

# Multi-arch (requires docker buildx, pushes to registry)
DOCKER_REGISTRY=ghcr.io/myorg/ DOCKER_TAG=v1.0.0 \
  make docker-multiarch

# Multi-arch local-only (current platform, loads into Docker)
make docker-multiarch-local

    Build args exposed by the Dockerfile:

    Arg Default Notes
    RUST_VERSION 1.94 Rust compiler in the builder-base stage (matches rust-toolchain.toml)
    FEATURES io-uring Cargo features to build with. ISA-L erasure coding is not one: every build has it.
    TARGETPLATFORM / TARGETARCH from buildx Set automatically by docker buildx

    Environment variables (containerised services)¶

    Most configuration goes via CLI flags in the container's command. A set of settings is also reachable via env vars (the full list is in configuration.md):

    Env var Service Purpose
    OBJECTIO_TOPOLOGY_REGION gateway Sets --topology-region
    OBJECTIO_TOPOLOGY_ZONE gateway Sets --topology-zone
    OBJECTIO_TOPOLOGY_DATACENTER gateway Sets --topology-datacenter
    OBJECTIO_TOPOLOGY_RACK gateway Sets --topology-rack
    OBJECTIO_TOPOLOGY_HOST gateway Sets --topology-host
    OBJECTIO_HOST_PROVIDER gateway Sets --host-provider (noop | k8s)
    OBJECTIO_HOST_PROVIDER_OSD_STS gateway OSD StatefulSet name (k8s provider only)
    POD_NAMESPACE gateway Namespace for host-provider RBAC (k8s only)
    OBJECTIO_MASTER_KEY gateway SSE-S3 master key (base64 32-byte)
    OBJECTIO_CONSOLE_DIR gateway Override the /_console/ static-asset dir
    OBJECTIO_TLS_CERT, OBJECTIO_TLS_KEY, OBJECTIO_TLS_CA all mTLS between services
    RUST_LOG all Overrides --log-level; same syntax as tracing

    Health checks¶

    • Gateway: GET /health answers 200 while the process is up; GET /_ready answers 200 once meta and enough OSDs answer (monitoring).
    • Meta and OSDs: GET /health on their metrics ports (9101, 9201).

    The all image declares no HEALTHCHECK: use these in your orchestrator. The per-service targets declare one, but the gateway's calls curl, which the image lacks, and the others always succeed.

    Troubleshooting¶

    "operation not permitted" on an OSD¶

    OSDs need CAP_SYS_RAWIO to open raw block devices with O_DIRECT (cap_add: [SYS_RAWIO], or privileged: true).

    "falling back to pread" in an OSD's log¶

    The image does its disk I/O through io_uring, and docker's default seccomp profile denies the io_uring system calls. The OSD (or aio) then logs storage error: io_uring setup for <device>: Operation not permitted (os error 1); falling back to pread for each device and serves with pread: correct, but slower. A privileged: true container, or a seccomp profile that allows io_uring_setup, io_uring_enter and io_uring_register (--security-opt seccomp=<file>), gets io_uring.

    Gateway can't reach meta¶

    Gateways and OSDs take every meta node's address in one comma-separated --meta-endpoint (for example http://meta1:9100,http://meta2:9100,http://meta3:9100); any one that answers serves them. Check that the names resolve inside the containers' network and that each meta node's --raft-advertise is an address the others can reach, not 0.0.0.0.

    Running ObjectIO in production¶

    What a production cluster needs, how to size it, what to alert on, and what to do when each alert fires. Read it with the failure-recovery, meta HA, metrics and upgrades pages, which go deeper on each subject.

    Before going live¶

    Every item is a default you have to change, or a requirement the software can't check for you.

    Requirement Why
    Redundancy Set an erasure code: ec.k/ec.m in the chart (its default is k: 1, m: 0, no redundancy), or --ec-k/--ec-m. 4+2 for 6–11 hosts, 8+4 from 12. With m = 0, one lost disk loses data.
    Hosts At least k + m OSD hosts, one more to rebuild onto (7 for 4+2). With fewer, placement puts several shards of a stripe on one host, and losing that host can lose data. Placement doesn't refuse it.
    Meta 3 meta nodes (5 for two failures at once), each on its own host. Raft needs a majority: 3 survive one loss.
    Authentication gateway.noAuth: false in the chart (its default is true). Without it anyone who reaches the gateway can read and write everything.
    mTLS tls.enabled: true (mTLS). Shards and metadata cross the network between services.
    Drives NVMe with power-loss protection, or a UPS for the whole host. An acknowledged write is fsynced; on a drive with a volatile write cache and no PLP, a power cut can still lose it.
    OSD layout Shards on the raw device; each OSD's state directory (--data-dir: metadata WAL and index) on a small partition of the same drive (about 2%), not the boot disk. Every metadata write fsyncs its WAL. With 18 OSDs on a host, a shared boot disk becomes the bottleneck, and its loss takes every OSD.
    Clocks NTP (chrony) on every host, offset well under 100 ms. A gateway whose clock is more than 500 ms from meta's refuses writes (503) until it is back in step: write order depends on clocks.
    Monitoring Prometheus scraping the gateways, meta and OSDs, the alert rules loaded, and the alerts routed to someone. Repair is automatic; deciding that a host is gone for good is not.
    Audit gateway.audit with a system bucket, if you need an audit trail (audit). Events are spooled to disk and delivered later, so a receiver outage loses nothing.

    Sizing¶

    Capacity¶

    usable ≈ raw × k / (k + m) × 0.95 − one host's worth (for rebuilds)
    • k/(k+m): 4+2 stores 1.5 bytes per byte (67% efficient), 8+4 the same, 10+4 1.4.
    • 0.95: an OSD refuses client writes past 95% of its disk (--full-ratio) and keeps the rest for repair, drain and backfill. Clients get 507 StorageFull.
    • One host's worth: when a host is lost for good, its shards are rebuilt onto the others. Keep that much free, or a host loss fills the cluster.

    Worked example: 8 hosts × 18 × 7.68 TB = 1,106 TB raw. 4+2: 1,106 × 0.67 × 0.95 = 704 TB, less one host (88 TB) = about 616 TB usable.

    Memory¶

    Since B22 an OSD's memory no longer depends on how many objects it holds:

    Per OSD
    Metadata index page cache --meta-cache-mib, 1024 by default
    Memtables (changes not yet checkpointed) up to 2 × 64 MiB
    Shard I/O buffers and the rest about 200 MB

    Plan about 1.5 GB per OSD with the default cache. Per host: 18 OSDs × 1.5 GB = 27 GB, plus the gateway (2–4 GB) and the OS. 64 GB per host leaves room. A smaller cache (--meta-cache-mib 256) cuts it to about 0.7 GB per OSD, at the cost of more metadata reads from disk for objects not read recently.

    Meta: plan 4–8 GB per node. Its index is in redb on disk, with a bounded cache.

    Metadata on disk¶

    Each object keeps a metadata copy on each of its k + m OSDs, about 600 bytes each, plus its shard location on each OSD holding a shard:

    OSD metadata per host ≈ objects_on_host × 6 copies / hosts × ~700 B

    For the example above at a 1 MiB average object: about 420 million copies per host, about 300 GB, roughly 16 GB per drive. That is why the state partition is about 2% of each drive.

    Throughput¶

    The performance page has the lab baseline. What bounds it: - Small PUTs wait for fsyncs. A drive with power-loss protection makes them cheap; one without doesn't. - Small GETs cost several internal calls each (B21 reduces them). - Large objects are bound by the network and by erasure coding: ISA-L on x86_64.

    Alerts¶

    The chart ships the rules in deploy/helm/objectio/alerts/objectio-rules.yaml: - its own Prometheus loads them when monitoring.enabled is set; - monitoring.prometheusRule.enabled also publishes them as a PrometheusRule for a prometheus-operator.

    Each alert has a runbook below.

    Alert Severity Runbook
    ObjectIOObjectsUnreadable critical Objects unreadable
    ObjectIOUnrecoverableStripes critical Objects unreadable
    ObjectIOObjectsAtRisk warning OSD down
    ObjectIORepairNotRunning warning Repair not running
    ObjectIOScrubStale warning Repair not running
    ObjectIOCorruptShards warning Corrupt shards
    ObjectIOMetaNoLeader critical Meta
    ObjectIOMetaElectionsChurn warning Meta
    ObjectIOMetaFollowerLagging warning Meta
    ObjectIOHealQueueFailing warning Meta
    ObjectIOGatewayClockSkewed critical Clock skew
    ObjectIOOsdDown warning OSD down
    ObjectIODiskNearFull warning Disks filling
    ObjectIODiskFull critical Disks filling
    ObjectIOClusterFilling warning Disks filling
    ObjectIOSlowShardSync warning Slow disk
    ObjectIOS3ServerErrors warning 5xx
    ObjectIOSpaceLeaking info 5xx
    ObjectIOAuditEventsDropped warning Audit
    ObjectIOReplicationLagging warning Replication
    ObjectIOSlowBlockJournal, ObjectIOBlockFlushFailing, ObjectIOBlockReadErrors Block

    Not covered by any alert yet: certificate expiry (no metric; watch cert-manager's own), meta data-dir free space (watch with node_exporter), and the audit spool's size.

    Runbooks¶

    Commands are obioctl (a SigV4 client of the gateway's admin API, bin/cli/README.md in the code repo) and meta's admin port (9102).

    An OSD is down¶

    What happens on its own. - Meta probes every OSD every 15 s. Three missed probes, about 45 s, mark it Down. - A Down OSD keeps its placement positions: writes go on at k + 1 shards (degraded), and reads decode around it. - Nothing is rebuilt while the OSD is merely Down. It may come back, and moving its data would cost more than waiting.

    What you do. 1. obioctl node list: which OSD, and since when. 2. If the process died: restart it (systemctl restart objectio-osd, or the pod). It rejoins, and repair rebuilds only the shards written while it was gone. 3. If the host or drive is gone for good: obioctl osd set-state <node_id> out. Repair then rebuilds its shards elsewhere. Do this within a few hours: until then every stripe it held is one failure from unreadable (ObjectIOObjectsAtRisk).

    Done when ObjectIOObjectsAtRisk clears and the repair counters (objectio_meta_repair_shards_rebuilt_total) stop rising.

    Replacing a disk¶

    1. If the disk still reads: obioctl osd set-state <node_id> draining, and wait for obioctl cluster drain-status to show it empty. It turns out by itself.
    2. If it doesn't read: obioctl osd set-state <node_id> out.
    3. Swap the drive and start the OSD on it with the same state directory: it keeps its identity, finds the disk blank, and forgets the shards it held there.
    4. obioctl osd set-state <node_id> in. Repair rebuilds what it held.

    Disks filling or full¶

    • Near full (85%). Plan capacity: add OSDs or hosts (the balancer moves data onto them), or delete data. Check obioctl cluster usage.
    • Full (95%). That OSD refuses client writes and clients get 507. The space above 95% is kept for repair. Other OSDs keep taking writes for stripes not placed on the full one.
    • Find which disks: objectio_disk_used_bytes / objectio_disk_capacity_bytes.
    • One full disk among emptier ones is uneven placement: the balancer evens it out (obioctl cluster rebalance status).
    • Everything full: add capacity. Deletes free space within a minute.
    • Don't raise --full-ratio to get writes going: it spends the room repair needs after the next failure.

    A gateway refuses writes for clock skew¶

    Its clock is more than 500 ms from meta's (objectio_gateway_clock_offset_seconds gives the offset). Writes through it fail with 503 (clients retry, ideally through another gateway). Reads work.

    Fix time sync on that host (chronyc tracking, chronyc makestep). Writes resume within a second of the clock coming back in step. Don't restart the gateway: it doesn't help.

    Meta has no leader, or elects often¶

    • No leader for more than a minute: fewer than a majority of meta nodes are up or can reach each other. Writes fail with 503; reads of object data mostly still work.
    • curl http://<meta>:9102/status on each node shows its role, its term, and who it thinks leads.
    • Bring a majority back. A node lost for good is replaced with POST :9102/add-learner then POST :9102/change-membership (meta HA).
    • No procedure exists yet for a majority lost for good.
    • Elections churn: usually a node that drops off the network intermittently, or a disk too slow for its heartbeats. Compare the nodes' objectio_meta_commit_seconds.
    • A follower lags: it is catching up, or its disk is slow. One far behind is sent a snapshot.
    • Heal queue failing: writes reached a quorum of metadata copies while meta was unreachable; gateways retry queuing them for 10 minutes. Persistent failures mean meta is down: see above.

    Repair not running¶

    objectio_meta_repair_last_pass_timestamp_seconds hasn't moved in three repair intervals (--repair-interval-secs, an hour by default). Repair runs on the meta leader: - check that there is one (above); - check the leader's log for repair: lines; - a pass that never ends is usually a target OSD that accepts connections but doesn't answer.

    Scrub stale: an OSD hasn't finished a scrub pass in 8 days. Check that OSD's log; a pass on a very full disk at 50 MiB/s (--scrub-rate-mib) can take days.

    Corrupt shards¶

    Scrub or a read found shards that don't match their checksums. The OSD reports them, and repair rebuilds them from the rest of the stripe. If the count keeps rising on one OSD, its drive is failing: check its SMART metrics (objectio_disk_smart_*) and replace it (above).

    Objects unreadable or unrecoverable¶

    Some stripes have fewer than k good shards: more failures at once than the code tolerates. 1. Bring back every OSD that is down but intact (powered off, network). Their shards make the stripes readable again. 2. Don't set OSDs out or wipe disks until this is resolved. 3. What can't be brought back is lost. No tool yet lists which objects are affected.

    A slow disk¶

    p99 shard fsync over 100 ms. Find the OSD from the per-OSD objectio_osd_disk_seconds. A drive getting slower often fails next: check SMART, and drain it (replacing a disk) if it doesn't recover. A drive without power-loss protection is always slow to fsync.

    S3 requests failing with 5xx¶

    • 503s during a fault are expected: clients retry.
    • Persistent 503s mean meta has no leader, OSDs are unreachable, or a gateway refuses writes for clock skew. See those runbooks.
    • A 500 is a bug: report it with the gateway's log line for the request id.

    Space leaking: shard deletes are failing, so freed space stays allocated until a later repair pass. It is usually an OSD that is down. A leak is never a loss.

    Audit events dropped¶

    Events are spooled on the gateway's disk until delivered. Drops mean: - the spool filled (--audit-spool-max-bytes) because a receiver has been down for long; or - a gateway pod was deleted without a clean shutdown.

    Fix the receiver; size the spool for the longest outage you accept (audit).

    Replication lagging¶

    The oldest unreplicated version is over an hour old. That is how much a loss of this site would lose. Check the target's reachability and credentials, and the result="error" count of objectio_replication_sent_total (replication).

    Block volumes¶

    The block gateway journals writes on its own disk before storing them as chunks. - Slow journal fsync: slows every block write. - Flush failing: chunks aren't being stored; the write cache fills and writes stall. - Read errors: reads that couldn't be served.

    The journal is a single copy on the block gateway's disk: losing that disk loses writes not yet flushed (a known gap; see the block design).

    Certificates expiring¶

    cert-manager renews 30 days before expiry. The services read their certificates only at start, so after a renewal restart them (rolling): kubectl rollout restart statefulset/<release>-meta statefulset/<release>-osd deployment/<release>-gateway. An expired certificate stops every internal call. There is no expiry metric yet: alert on cert-manager's certmanager_certificate_expiration_timestamp_seconds.

    Upgrades¶

    Follow upgrades: meta first, then OSDs, then gateways, one at a time. Then obioctl upgrade status, and obioctl upgrade finalize once every node runs the new release. Back up meta.redb from a stopped follower first.

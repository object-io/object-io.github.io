    ObjectIO¶

    S3-compatible object storage in Rust, built to not lose data. One storage core (erasure coding, failure-domain-aware placement, repair, metadata on Raft) with S3, data-lake catalogs and block volumes on top of it. Apache-2.0, every feature, no tiers. Source on GitHub.

    docker run --rm -p 9000:9000 -v objectio-data:/var/lib/objectio \
  ghcr.io/object-io/objectio:latest objectio-aio --data /var/lib/objectio

    That's a whole cluster in one process: meta, OSDs and the S3 gateway on port 9000. The quickstart has the binaries for Linux and macOS, and a 3-meta, 6-OSD cluster in Docker Compose; Kubernetes has the Helm chart.

    Where it stands¶

    ObjectIO is pre-1.0. The S3 gateway and the storage core are on the way to a release candidate; every gate for it is a row in the roadmap, with its exit test.

    Status
    S3 Passes all 591 applicable ceph s3-tests on Linux x86_64 and arm64. Versioning, Object Lock, lifecycle, multipart, checksums, SSE, bucket policies, IAM users and groups, tenants, replication between clusters
    Storage core Erasure coding (Reed-Solomon, ISA-L or pure Rust), placement groups across failure domains, repair, drain, backfill, balancer, small-object packing, scrub; raw disks with O_DIRECT and io_uring
    Meta Raft (openraft) on 3 or more nodes; any node serves; log compaction and snapshots
    Data lake Iceberg REST Catalog, Unity Catalog API and Delta Sharing are built; tests with real engines (Spark, Trino, pyiceberg) come next
    Block Volumes over NBD: thin provisioning, snapshots, clones, a write journal fsynced before the ack. Filesystem and database crash tests are the gate for production
    File NFS on the same core, later

    What "durable" means here¶

    • An acknowledgement means the data is on stable storage. Every shard is fsynced, and its location record after it, before the PUT returns. Nothing trades this for speed.
    • No single copy decides. An object's shards are spread across failure domains (hosts by default; racks or zones if you declare them), and its metadata is kept with them on every OSD of its placement, written at a majority and read from a quorum, newest copy winning.
    • Every byte is checked twice. Each shard's checksum is recorded with the object when it's written and checked on every read and every repair, independently of the checksum the disk keeps.
    • Repair is continuous. A lost disk or host is rebuilt from the surviving shards onto the rest of the cluster, without an operator.

    How it's tested¶

    Test What it shows Latest
    S3 compatibility ceph/s3-tests, the suite Ceph RGW is built against, on Linux x86_64 and arm64; every failure labelled with why 591 of 591 applicable pass
    Chaos A six-machine cluster under writes from two gateways while the meta leader is killed, hosts lose power, the network is cut and disks are pulled. Every acknowledged object is read back after each fault Passes; writes paused at most 5.4 s
    Crash consistency The OSD's disk writes recorded and replayed up to random points, as a power cut would leave them: every acknowledged write must survive 80 cuts, nothing lost
    Long soak 48 hours on a lab host: overwrites and deletes, disks filling, OSD and host failures, repair, and an audit of every key at the end Running
    Performance Side by side with RustFS and SeaweedFS, same client, same disk Single-host baseline published
    Every pull request Unit and end-to-end tests against real processes, a meta HA test on Kubernetes, and a rolling upgrade from the last release under traffic

    ObjectIO — features and roadmap¶

    Every feature, its status, and the milestones ahead. Details of each built feature are in the feature reference.

    Last reviewed: 2026-10-05, at objectio main after #158.

    Priorities¶

    1. S3: production-ready and bug-free. The product we ship first. No known bug stays open; every gap is either closed or written down as "not supported" with the reason.
    2. The storage engine core, worked on alongside S3: OSD, erasure coding, placement, meta, repair. Everything here is built once and reused by block and file — none of it is S3-specific.
    3. Data lake (Iceberg REST, Unity Catalog, Delta Sharing): next, and as important as S3 once S3 is in production.
    4. Block, then file, on the same core.

    Rule for every track: reliability first. An acknowledgment means the data is on stable storage; nothing trades durability for speed.

    Now / next / later¶

    Track Item
    Now S3 + core Release-candidate gates: the 48-hour soak (B2) is running; meta recovery after a power cut (B25) and S3 Select (A16) next
    Next S3 + core Multi-host performance numbers and a regression check in CI (B4); fewer round trips on small GETs (B21); then the release candidate (A9)
    Next Data lake End-to-end tests with real engines (pyiceberg, Spark, Trino, Delta Sharing client)
    Later S3 Replication phases 2 (resync, bandwidth) and 3 (two-way)
    Later S3 Tenant audit options: own bucket, export, viewer, Kafka (A10, A11, A13)
    Later Block QoS enforcement; filesystem/database crash tests
    Later File NFS gateway design

    Audit: how it works for each kind of user¶

    • The system always audits. With A8c, every request is an event, fsynced to the gateway's spool before delivery, and kept in an internal system bucket with a retention period the operator sets (optionally under Object Lock, so events can't be altered or removed). The operator's webhooks, Kafka, file and stdout targets get a copy.
    • A tenant opts in (tenant admin), choosing any of:
    • into a bucket of its own: its events as compressed JSON-lines objects partitioned by date (<prefix>/2026/10/03/…), readable with any S3 tool or a query engine;
    • streamed: to its webhook or Kafka (on hosts the operator allows);
    • exported on demand: a time range downloaded from the API or the console, from the system's copy;
    • as S3 bucket logging: PutBucketLogging per bucket, in AWS's access-log format, for tools that expect it.
    • A tenant only ever sees events on its buckets or by its principals.

    B23 End-to-end shard checksums (design) Each shard's checksum is kept in its ObjectMeta when written, not only by the OSD that holds it; a GET checks every shard it decodes from against it, repair checks its sources and the shard it rebuilt before storing it, and scrub reports a mismatch as corrupt. Exit: a test that stores a wrong shard on an OSD (with a matching OSD-side checksum) gets an error or a repaired read, never the wrong bytes; the B2 disk-pull fault passes ✅
    B24 Repair throughput Rebuilding is parallel across objects and OSDs, bounded so client I/O keeps priority: a replaced 7.68 TB drive of 1 MiB objects rebuilt in under 8 hours on the lab host (today about 50 shards/s, so about 40 hours); the chaos disk-pull fault restores full redundancy within 15 minutes 🔨 #161 (10 → 67 shards/s)

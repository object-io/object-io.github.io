    Performance (B4)¶

    ObjectIO next to RustFS (and SeaweedFS on one host), measured with the same client on the same machines and drives: a single-host baseline, and six cloud VMs with local NVMe. Every change is checked against the tree it lands on by a regression check in CI. What drives without power-loss protection cost, and what is still to measure on drives with it, is under drives. Where the CPU goes is in profiling (B28).

    The regression check in CI¶

    The performance job in the code repo's CI runs in the merge queue, so every change is measured before it lands (it doesn't block a merge until it is made a required check), and on a pull request labelled perf (add the label, then push: a label alone doesn't start a run). It builds the tree that lands and the tree it lands on (the base), both release builds with ISA-L and io_uring, and runs scripts/bench/regression.py on them.

    What it runs. Each build five times, in turn on the same runner: base, head, head, base, and so on. Every run starts a fresh objectio-aio (six OSDs, 4+2) and, with objectio-s3-bench, puts 6,000 objects of 64 KiB (32 in flight) and gets each of them four times, then puts 400 objects of 4 MiB (8 in flight) and gets each three times. A short unmeasured warm-up comes first.

    How it decides. For each of the four cells (PUT and GET, 64 KiB and 4 MiB), the head's median throughput is divided by the base's. Any cell below 0.85 fails the job. p99 latency is shown next to it but not judged: on a shared runner it moves too much from run to run.

    Why it is built this way.

    • Relative, on one runner. GitHub's runners differ from one another by more than most regressions, so no absolute number can gate anything. Both builds run on the same runner in the same job, and alternating them means a runner that slows down part way through slows both.
    • Medians of five. One run in five can be off by a quarter (a cold first run, a noisy neighbour); the median ignores it.
    • Data in memory. The aio keeps its data on a tmpfs. On a runner's disk, one build's 64 KiB PUTs went from 208 to 372 a second between runs, more than any regression this is for. In memory the check measures the software (CPU, copies, RPCs, locks), which is what changes from commit to commit.

    What it doesn't see. A change that adds work on the drive (another fsync per PUT) costs almost nothing in memory, so it passes here. Drive costs are measured by the baselines below, on real drives, and by the soak.

    Reading it. The job summary has a table:

    Cell Base Head Head ÷ base p99 (not judged)
    PUT 64KiB 1,237 ops/s (±1%) 1,235 ops/s (±7%) 1.00 ✅ 85 → 88 ms

    The ± is half the range of the five runs. A wide range on either side means that cell was noisy on this runner. The artifact performance has every run's numbers (perf.json) and each aio's log. To run it locally:

    cargo build --release --features objectio-aio/isal,objectio-aio/io-uring \
  --bin objectio-aio --bin objectio-s3-bench          # on each tree, into two directories
scripts/bench/regression.py --base <dir> --head <dir> --workdir <a tmpfs>

    The work directory must not be under /dev: an OSD takes a path there for a device.

    How well it works.

    Runs on GitHub's runners (objectio#211 for no change, and a throwaway pull request that added 1 ms of CPU to every PUT, about 30% of a 64 KiB PUT's CPU on a runner and almost none of a 4 MiB PUT's):

    Run PUT 64KiB GET 64KiB PUT 4MiB GET 4MiB Verdict
    No change 1.01 1.00 1.05 1.02 pass
    No change, another runner 1.01 1.01 1.08 0.99 pass
    1 ms more CPU in every PUT 0.78 1.00 0.95 0.96 fail: PUT 64KiB

    The two "no change" runners differed by 65% in absolute speed (1,151 against 1,906 PUTs of 64 KiB a second); the ratios stayed within 1%. Getting there:

    • On the runner's disk, the first version caught a 15 ms sleep in every PUT (PUT 64 KiB at 0.83), but on that runner the base alone ranged from 208 to 372 PUTs a second. Its data moved to a tmpfs.
    • With a 4 MiB phase of 1.5 s, one no-change run came out at 0.87 for PUT 4 MiB, too close to the threshold. The phase now writes 400 objects instead of 150.

    So it fails a change that costs a cell about 20% of its throughput or more; a smaller loss usually passes, so it is no substitute for the baselines. 4 MiB PUTs are the noisiest cell (one runner's runs spread ±24%).

    Drives with and without power-loss protection¶

    An acknowledged PUT waits for a flush on every OSD it writes to. On a drive with a volatile write cache and no power-loss protection (PLP), a flush empties that cache to flash; on one with PLP, capacitors cover the cache, so the drive can acknowledge a flush without emptying it. Small PUTs, which are mostly flushes, gain the most.

    Measured: the drives we have, both without PLP. The lab host of the single-host baseline has two consumer NVMe drives. Both report a volatile write cache, and neither has PLP. 4 KiB writes, each followed by fdatasync, one at a time (3,000 of them, 2026-10-15; other tests were running on the host):

    Drive Volatile write cache Flush p50 Flush p99 Flushes a second
    Corsair MP600 Elite 2 TB (the baselines' drive) yes 0.67 ms 0.89 ms 1,440
    OEM 1 TB, Phison controller (ESL01TBTLCZ; through LVM) yes 0.25 ms 0.58 ms 3,670

    The six cloud VMs' local NVMe was not checked for a volatile cache while they ran, and they are gone.

    Not yet measured: a drive with PLP. None is within reach without making cloud machines for it, and production hosts are not ours to benchmark. This part of B4 is open. When a machine with enterprise NVMe is available:

    1. Check the drive: nvme id-ctrl /dev/nvme0 | grep vwc (0 means no volatile write cache, what a drive with PLP usually reports), and cat /sys/block/nvme0n1/queue/write_cache (write through means the kernel sends it no flushes).
    2. Measure a flush: fio --name=flush --filename=<a file on the drive> --rw=write --bs=4k --size=64m --ioengine=sync --fdatasync=1, and compare its sync latencies with the table above.
    3. Run the small-object cells (PUT 4 KiB and 64 KiB, as in the baselines below) on that machine and on one without PLP, same client.

    The operations guide already requires PLP (or a UPS) for production: without it, a power cut can lose what the cache held, whatever the speed.

    Six cloud VMs: 2026-10-07¶

    Machines: six Azure Standard_D4pds_v6 in Central India, made with objectio-infra (./infra up azure): 4 Arm vCPUs (Cobalt 100), 16 GB, one local NVMe drive (220 GB) each, accelerated networking, one private network. Ubuntu 24.04.

    Systems, each on the same six drives in turn (the drives erased in between):

    Version Layout Durability of an acknowledged PUT
    ObjectIO main of 2026-10-07 with objectio#181 and #182, release build, aarch64 (erasure coding by rust-simd: ISA-L is x86 only) meta on nodes 1–3, an OSD and a gateway on every node, 4+2. Each drive: 16 GiB for meta, 32 GiB for the OSD's metadata, the rest raw for the OSD shards and metadata at write quorum, fsynced
    RustFS 1.0.1, aarch64 one server per node, one pool of six drives, XFS, EC:2 (4+2; checked: a 4 MiB object puts 1,048,704 bytes on each drive) erasure-coded at write quorum, fsynced

    Meta shares each drive with the OSD here (these VMs have one fast drive); the guide gives it a drive of its own, and the p99 of PUTs pays for it (see below).

    Client: warp 1.1.4 on node 1, spreading requests over all six nodes' S3 ports, 60 s per cell, 64 concurrent requests (32 for 4 MiB). The scripts are objectio-infra's deploy and bench.

    Results¶

    Throughput (median, p99 latency).

    Cell ObjectIO RustFS ObjectIO ÷ RustFS
    PUT 4 KiB 1,921 obj/s (29 ms, 80 ms) 291–382 obj/s (148–203 ms, 0.8–1.1 s) 5–6.6
    PUT 64 KiB 1,496 obj/s (33 ms, 341 ms) 348 obj/s (139 ms, 812 ms) 4.3
    PUT 4 MiB 966 MiB/s (125 ms, 383 ms) 787 MiB/s (150 ms, 303 ms) 1.2
    GET 4 KiB 8,316 obj/s (8.4 ms, 26 ms) 4,532 obj/s (13.3 ms, 50 ms) 1.8
    GET 64 KiB 6,334 obj/s (10.9 ms, 29 ms) 4,205 obj/s (14.0 ms, 54 ms) 1.5
    GET 4 MiB 2,759 MiB/s (43 ms, 115 ms) 2,544 MiB/s (45 ms, 125 ms) 1.1

    What it shows¶

    • Small objects: ObjectIO is ahead, on PUT by 4–6 times. A small PUT is one round trip to the OSDs and one flush on each (B21): the shards go with the object's metadata, into the OSDs' metadata logs, which batch concurrent writes into one fsync.
    • Small GETs: 1.5–1.8 times RustFS, where the single host had RustFS 3–4.5 times ahead: the GET is one round trip (B21), and the single host's loopback RPC costs are gone.
    • Large objects: within 1.2 times, ObjectIO ahead. Both are bound by the network and the drives.
    • The p99 of small PUTs (341 ms at 64 KiB) is meta sharing its drive with the OSD: an OSD's metadata checkpoint holds back meta's syncs (see the hardware guide). The median is 33 ms.

    Found along the way and fixed (details in profiling):

    • A regex compiled for every request's Authorization header: 27% of a gateway's CPU (objectio#181).
    • Every gateway's poll made every OSD scan all its object metadata: 20% of an OSD's CPU, and growing with the objects held (objectio#182).
    • Meta killed in its first seconds could never start again; an OSD given a missing /dev path ran on a file in memory (objectio#183).

    Single host: 2026-10-04¶

    Host: one lab machine. AMD Ryzen 9 7945HX (16 cores, 32 threads), 64 GB RAM, one consumer NVMe (Corsair MP600 Elite: volatile write cache, no power-loss protection), ext4, Linux 6.8. Everything runs on this one host, client included.

    Systems:

    Version Layout Durability of an acknowledged PUT
    ObjectIO main at #143, release build (isal, io-uring) objectio-aio: meta, six OSDs and the gateway in one process; 4+2 erasure coding; each OSD a 64 GiB sparse file shards at write quorum (5 of 6), each fsynced
    RustFS rustfs/rustfs:latest (image of 2026-10-03) one server, six directories, EC:2 (4+2) erasure-coded at write quorum, fsynced
    SeaweedFS 4.48 weed server (master, volume, filer, S3) with its defaults one copy, not fsynced per write

    The six "drives" of ObjectIO and RustFS share one device here. That is fine for comparing the software, not for absolute numbers: on separate drives both would write in parallel.

    SeaweedFS's defaults keep one copy and don't fsync each write, so its PUT numbers are not comparable with the other two. They show what that trade-off buys, not a like-for-like result.

    Client: warp 1.1.4. For each object size, PUT then GET, 32 concurrent clients, 30 s per cell. The script is scripts/bench/baseline.sh in the code repo.

    Results¶

    Throughput (p99 latency). ObjectIO and RustFS ran each cell up to 3 times; the range is shown where the runs differed by more than 10%.

    Cell ObjectIO RustFS SeaweedFS (one copy, no fsync)
    PUT 4 KiB 553–558 obj/s (195 ms) 353–477 obj/s (135 ms) 21,388 obj/s (4.3 ms)
    PUT 64 KiB 236–239 obj/s (223 ms) 348–373 obj/s (145 ms) 13,913 obj/s (7.5 ms)
    PUT 1 MiB 111–241 MiB/s (423 ms) 183–217 MiB/s (239 ms) 1,595 MiB/s (168 ms)
    PUT 16 MiB 486–772 MiB/s (1.3 s) 503 MiB/s (2.8 s) failed (internal errors)
    GET 4 KiB 8,403–10,511 obj/s (5.9 ms) 31,692–32,918 obj/s (2.0 ms) 20,203 obj/s (3.9 ms)
    GET 64 KiB 5,392–5,808 obj/s (9.7 ms) 25,613–27,141 obj/s (2.4 ms) 18,931 obj/s (4.2 ms)
    GET 1 MiB 1,785–1,954 MiB/s (25.7 ms) 2,419–2,479 MiB/s (105 ms) 3,734 MiB/s (16.7 ms)
    GET 16 MiB 1,716 MiB/s (415 ms) 2,304 MiB/s (386 ms) not run (the PUT failed)

    What it shows¶

    • Durable PUTs are bound by the disk. ObjectIO and RustFS both fsync before they acknowledge, and both land in the hundreds of small PUTs a second on this drive. A drive with power-loss protection makes an fsync nearly free; this one doesn't. SeaweedFS is 40–60 times faster because it skips that work.
    • 64 KiB PUTs: RustFS is 1.5 times faster. RustFS writes each drive's erasure-coded piece of a small object inside that drive's metadata file (xl.meta; seen here for 64 KiB and 256 KiB objects), so a small PUT is one fsync round. ObjectIO inlines only objects up to 4 KiB (--inline-max-size), whole, on every copy. A 64 KiB object takes two rounds: shards, then metadata (B21 makes it one).
    • Small GETs: RustFS is 3–4.5 times faster. RustFS reads its own drives. ObjectIO's aio is a cluster in one process: a GET makes one RPC to meta for the placement and asks all six OSDs for the object's metadata, then reads shards (none for an inline object). That is 7 RPCs for a 4 KiB GET and 11 for 64 KiB, each over loopback HTTP/2. Under profiling, nearly all the CPU goes to that RPC work and to lock contention inside h2. In a multi-host deployment RustFS makes these calls too, so this gap is partly an artefact of one host. But fewer round trips per small GET is a real gain everywhere: B21.
    • Large objects: within 1.3 times. At 1 MiB and above both are close to the device and to the CPU cost of erasure coding.

    Found along the way and fixed:

    • warp could not create buckets: the gateway refused PUT /bucket/ with the trailing slash that minio-go clients send (#143).
    • The OSD's metadata cache scanned its lists on every lookup: +7% on small GETs (#144).
